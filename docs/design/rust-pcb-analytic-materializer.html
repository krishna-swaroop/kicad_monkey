Rust PCB analytic materializer

Status: proposal. This work lives on the krishna-swaroop/kicad_monkey fork, branch feat/rust-analytic-materializer, until issue #20 closes its contract upstream. Upstream has said it will bring a materializer into kicad_monkey after building one in the altium_monkey Rust port. That implementation is not public yet, so this work follows kicad_monkey's current crate and contract layout. It also keeps every consumer behind the packed encoding, so that adopting the upstream producer later changes the producer and nothing else.

KiCad source -> resolve physical intent -> analytic materialization -> adapters

The materializer is the single source of board geometry for two consumers. The KiCad-Prism WebGPU viewer draws it. The prism-sim-studio engines mesh it. Because both read the same operations through the same stable operation indices and the same (slice, tile) chunks, simulation results come back keyed to geometry the viewer already draws. The viewer can then overlay those results on the board without a second geometry pipeline.

Layout in kicad_monkey

The layout follows existing producers. board_plotter_ir is a module in kicad-monkey-core. Its contract is authored in TypeSpec and generated into kicad-monkey-contracts, and its serializer, kicad-monkey-svg, is a thin separate crate. The materializer is laid out the same way:

Decision summary

  • Vocabulary. The crate uses the issue #20 vocabulary exactly: disk_2d, rect_2d, rounded_rect_2d, chamfered_rect_2d, trapezoid_2d, capsule_2d, annulus_2d, swept_path_2d (line, arc, and cubic Bézier segments with width, cap, and join), and planar_region_2d, whose contours use the same segments. The cubic segment is an addition to the issue #20 sketch. It is the exact form of KiCad's curves on pads, graphics, and the board edge, and it will be proposed upstream. Consumers that cannot evaluate cubics directly, for example an SDF stroke shader, lower them at their own tolerance. Every operation also carries one composed Affine2D, one material role, one slice, and a resolved net_key. Holes are separate operations.
  • Analytic only. The crate performs no Boolean operations, no offsetting, and no tessellation. Material that is removed (mask openings, dielectric drills, profile cutouts) is written as subtract operations, and consumers resolve them. The Geometer gate in the bridge-entry disposition therefore stays closed. Profile contour closure is the one new close-to-format operation.
  • Scope beyond the first slice of issue #20. The binding table is required. The crate also covers:
    • differential pairs and net-class rules;
    • via protection, back-drill, and plating thickness;
    • dielectric regions and the board profile;
    • mask, paste, and silkscreen;
    • component bodies;
    • the full stack, with the material facts KiCad provides.
  • Encoding. Columnar 32-bit nanometre values in KiCad's board frame (X right, Y down), chunked by (slice, tile) and listed in a chunk index. The JSON and S-expression views are deterministic debug output.
  • Platforms. Linux x64 and arm64, macOS arm64 and x64, and Windows x64. The producer and pack crates must also build for wasm32-unknown-unknown. No native SDK is linked, and unsafe_code stays forbidden.

One geometry for viewing and simulation

These are the invariants that let the WebGPU viewer draw both the board and simulation results from one materialization:

  1. Same operations. The viewer's copper, mask, and substrate draws, and every engine's mesh, come from the same materialization. Each consumer only lowers it at its own tolerance. No producer writes geometry that only the viewer or only the solver can see.
  2. Same identity. Operation indices are stable across the packed columns, the binding table, render feature IDs, and engine element-to-operation maps. A pick in the viewer and a result row in a solver name the same operation.
  3. Same chunks. Engines report spatial results per (slice, tile), using the materialization's tile grid. The viewer already loads, budgets, and evicts per slice and tile, so result overlays follow the same rules: inner layers load on demand, budgets are counted, and data is evicted together with the geometry tile it belongs to.

Simulation results therefore come back in two forms. Both forms are defined in prism-sim-studio's result contract.

FormContentViewer use
Per-operation values A value per operation index for a named quantity. Examples: current through each via, temperature of each component body, maximum current density per track. A lookup buffer indexed by the feature ID the viewer already writes per vertex and reads back on pick. It colors features through a colormap and shows the exact value on hover.
Field tiles A scalar raster per (slice, tile) in board nanometres, with resolution, value range, and units. Examples: voltage, current density, temperature. Sampled in the fragment shader at the fragment's board position, masked by the geometry already being drawn. This works the same whether the geometry is a mesh today or an SDF instance after the analytic spike.

The viewer's geometry, tiling, culling, LOD, picking, and budget code is reused as is. The overlay adds one shading mode: a colormap, a per-feature value buffer, and a field-tile texture binding. It is added as a new pipeline family, so the pinned base shaders stay untouched. Engines may still write their native meshes as debug artifacts. They are not the display path.

Changes outside the materializer

The materializer is not confined to its own module. This branch also changes:

  • PCB decoding (pcb.rs, pcb/decode.rs, pcb/setup.rs, pcb/vias.rs, pcb/zones.rs, pcb/indexing.rs, pcb/footprints.rs):
    • layers and mask margin on tracks and arcs;
    • board mask, paste, and tenting setup;
    • the legacy footprint paste-ratio spelling;
    • dielectric sub-layers;
    • the legacy per-via tenting form;
    • whether a zone declares filled_areas_thickness;
    • zones inside footprints.
  • Text (newstroke.rs): the KiCad-exact entry point realize_newstroke_kicad_a0, with KiCad's italic shear and line positions.
  • Exports (lib.rs): the new PCB records and the text entry point.
  • Contracts:
    • the a0 contract, its validator, chunking, and the scope filter;
    • ValidationError, moved to its own module;
    • codegen hooks for the materialization schemas;
    • inline array lengths in the Python generator.

Contract: kicad_monkey.materialization.a0

  • Scope: the requested products, slices, nets, and region, the tile size, and whether the result is complete.
  • Coordinate system: nanometres, with X pointing right on the board and Y pointing down. Z is derived from the slice order.
  • Stack: conductor, dielectric, solder mask, paste, and silkscreen slices. Each slice has a key, role, order, optional thickness, material name, εr, and tanδ, plus mask data and the finish.
  • Nets: net_key, name, and class. Net classes carry width, clearance, differential-pair width and gap, and via sizes. Differential pairs name a positive and a negative net_key.
  • Surface operations: index, action, material, slice_key, net_key, shape, affine, and the bounds after the affine is applied.
  • Hole operations: index, shape, affine, plating, start and end slices, net_key, plating thickness, protection for each side, back-drill, and bounds.
  • Components: reference, footprint, side, affine, body box, and body height when known.
  • Binding table (required, separate): for each operation, the source_uid, source_kind, refdes, pad_number, and net_key.
  • Chunk index: for each (slice, tile), the bounds, the net_keys, and the range of operation indices. The pack's section directory adds each chunk block's byte offset.

Correctness rules

  1. Projection input and full-model input produce identical results.
  2. A selective result equals the complete result filtered the same way.
  3. Output is byte-deterministic for the same source and producer version.
  4. Operations on different nets are never merged.
  5. Every operation has a slice. Every conductive operation has a net_key; copper with no net uses the empty net.

Packed encoding

  • Columns. Each shape kind has fixed-width columns of 32-bit signed nanometre parameters, plus a shared affine column. Rotation and scale are stored as f64 and translation as integer nanometres. Renderers convert these to f32 relative to each tile's origin.
  • Chunks. Data is chunked by (slice, tile), and the tile size is a request parameter. An operation belongs to the tile that contains the centre of its bounds. A chunk's bounds cover every operation it holds.
  • Header. The header holds the schema version, producer version, source hash, scope, and chunk directory. Readers seek straight to the chunks they need.
  • Byte layout. The byte layout is specified here and in the pack crate's module docs, because TypeSpec cannot express a binary layout. TypeSpec governs the JSON header and the debug document.
  • Layout (format 0). All values are little-endian, and every section starts on 8 bytes. The pack is, in order:
    • a 16-byte preamble: magic, version, flags, and header length;
    • the JSON header: the document without operations, binding, or chunks;
    • a section directory of offset and length pairs;
    • these binary sections:
      • String table: every source UID, refdes, pad number, and group key once. A lowercase canonical UUID takes 16 bytes.
      • Binding: columns of string, net, and operation indices.
      • Chunk directory: columns of slice index, tile, bounds, operation range, and net indices.
      • Linear-part table: each distinct affine m11 m12 m21 m22 once, as f64.
      • Column blocks: one per chunk, as a struct of arrays. Each operation has a linear index, an int32 translation, int32 bounds, slice, net, group, and offset indices, a parameter start, and kind, material, and shape bytes. The int32 parameter stream holds the shapes and hole details, with path segment tags packed 16 to a word.
  • Reading. PackReader::open reads the header, binding, and chunk directory and checks the operation-independent rules. A chunk then decodes on its own, and document() decodes everything and validates it. Values round-trip exactly, f64 bits included. Damaged or truncated packs fail closed; tests flip and cut every byte.
  • Size. A pack is about 19 to 21% of the JSON debug view on the corpus. JTYU-OBC is 13.7 MB against 70.9 MB of JSON, and zone fills, at 8 bytes per vertex, are most of what remains. The corpus gate round-trips every complete document through the pack.

Slice 0 contract decisions

  • Decoding. The workspace builds serde_json with arbitrary_precision. With that feature, numbers inside untagged unions do not decode straight from text. Documents are therefore decoded through materialization_contract::decode_materialization_document_a0, which parses to a Value first and then runs the semantic validator. The pack header reader does the same with validate_materialization_header, which applies every rule that holds without operations and takes the operation count from the chunk directory.
  • Exact kinds. Every shape, segment, and operation checks its literal kind during decoding. The codegen injects these checks from kicad-monkey-codegen/src/materialization_projection.rs.
  • Hole chunks. A hole is chunked on its start slice. A slice filter keeps a hole when the hole's span crosses any selected slice.
  • Empty filters. An empty slice_keys or net_keys list means all slices or all nets. Generated types cannot tell an absent list from an empty one.
  • Chunk contents. Chunk bounds are the union of the bounds of the operations in the chunk. Chunk net keys are the sorted, distinct nets of those operations. The producer and filter_document both build chunks with chunk_operations, so rule 2 compares like with like.
  • S-expression view. It is a debug view generated from the JSON, with sorted keys. It is not parsed back.

Slice 1 status

Slice 1 emits the copper and holes products. Copper covers tracks, track arcs, via lands on each flashed layer, stored zone fills, and pad lands. Holes cover vias and pads. Slice 1 also emits the net table, a binding entry for every operation, and component records. Conductor slices are named copper.front, copper.inN, and copper.back. The full stack follows in slice 2.

Decisions

  • Placement. Via lands and holes are local shapes centred on the origin and placed by a translation affine. This makes them instanceable. Tracks and zone fills keep the identity affine and board coordinates.
  • Custom pads. A custom pad emits its anchor shape as well as each primitive. Polygon primitives keep authored arcs as arc segments, and Bézier strokes become one swept path with a single cubic segment.
  • Conditional flashing. Pads and vias that remove unused layers, keep end layers, or carry zone-layer connections take their flashed layers from core's board plot facts. Presentation forms are blanked first. The document records this with a plot_facts_flash_layers diagnostic.
  • Scoped diagnostics. Diagnostics carry an optional product. A selective result keeps only the diagnostics of its products, so rule 2 holds for diagnostics as well as for operations.
  • Exact bounds. Disks, annuli, and capsules placed by a similarity affine get exact bounds. Cubic segments get exact bounds from their per-axis turning points, not their control-point hull. Other shapes use the transformed local box, which is exact for rectangles and conservative for curved shapes.
  • Undecodable zones. A copper zone that fails to decode is reported as zone_not_decoded. It is never dropped silently.

Slice 2 status

Slice 2 adds the full stack, board profile closure, the dielectric product, and hole protection and back-drill.

Decisions

  • Stack. The stack follows the KiCad stackup front to back. The stackup layer type gives each slice its role: silkscreen, paste, solder mask, conductor, or dielectric. Thickness, material, εr, and tanδ are copied only when stated. Keys are silkscreen|paste|mask.front|back, the copper keys, and dielectric.N. The stackup is used only when its copper layers equal the board's copper layers. Otherwise, and when the board has no stackup at all, the stack is an explicit default of the same shape with every physical value unknown. A stackup_absent or stackup_mismatch diagnostic records which case applied. Board thickness and copper finish are recorded.
  • Profile closure. Board and footprint Edge.Cuts carriers become exact edges in the board frame: lines, arcs, and cubics. Rectangles, circles, and polygons are already closed loops. Open edges are chained end to end within 10 µm (Euclidean, KiCad's outline chaining epsilon), and reversed when needed. Endpoints are looked up in a grid one tolerance wide, so chaining is near linear. Loops below 1e-4 mm² are dropped. Loops nest by even-odd containment: each even-depth loop is a region, and the loops directly inside it are its cutouts, which also handles panels. Unclosed edges are reported as outline_not_closed, and a board with no loop gets outline_absent.
  • Contour closing. When the last segment of a contour does not end at its start, a straight closing segment is implied.
  • Dielectric. Each dielectric slice adds every profile region, with its cutouts as holes. It then subtracts the drill shape of every hole whose copper span crosses that slice.
  • Back-drill bores in the dielectric. Each back-drill or tertiary drill with a diameter and a copper end layer also subtracts a disk of its diameter, centred on the hole, from every dielectric slice between the drilled outer copper layer and the end layer. This matches KiCad's own 3D model, which removes the bore on every copper layer from the start layer to the end layer inclusive. A back-drill without a diameter or without a copper end layer cannot be placed. The dielectric keeps only the primary hole for it, and a backdrill_not_cut warning names the hole. The bore is not yet subtracted from copper lands on the drilled layers.
  • Hole protection. Via tenting, covering, and plugging (per side), filling, and capping are copied as authored, and unspecified defers to the board setup.
  • Back-drill. Back-drill and tertiary drill records give the drilled side from the start layer, the diameter, and the authored end layer.
  • Plating thickness. KiCad does not state it, so it stays unknown. It is supplied downstream through prism.materials.

Evidence

  • Profile on the corpus. Profiles close with no diagnostics on all five corpus boards:
    • 4-ch-backplane: four lines and four arcs, one region.
    • speedy_processing_module: 48 footprint-owned edges, one region.
    • charge_indicator: one region and eight circular cutouts.
    • taillight: one region and eight circular cutouts.
    • JTYU-OBC: one region.
    An independent count of each board's Edge.Cuts carriers agrees.
  • Cross-check with KiCad-Prism's board body. With the Geometer SDK for macOS arm64 (2026.9.19, checksum verified), prism-kicad-native compile-board-body runs on all five corpus boards. Its profile ring count and drill count equal our profile regions plus cutouts and our hole operations on every board. The outline box matches to the nanometre on four boards. On charge_indicator, whose outline is four large-radius arcs, ours is up to 4.9 µm larger, within Prism's 5 µm mesh tolerance: Prism measures the triangulated arcs, which lie inside the true arcs.
  • Exact arc bounds. The cross-check found that arc bounds used the whole circumcircle box, which was safe but up to hundreds of millimetres loose on large-radius arcs. An arc's box is now its end points plus only the circle's axis extremes that it sweeps, rounded outward.
  • Stackups. Stackups resolve with 9 to 25 slices of known thickness.
  • Rule 2. Rule 2 held for every per-slice scope of copper, holes, both together, and dielectric: 52 to 116 scopes per board.
  • Tests. The slice tests cover the stackup mapping, an outline drawn from mixed-direction board and footprint edges with an arc and a cutout, via protection and back-drill, and rule 2 with dielectric. A four-layer board checks that a back-drill from B.Cu to In2.Cu cuts only the bottom core, that an unplaceable back-drill is reported, and that rule 2 still holds. No corpus board has back-drills, so these tests are the only evidence for the bore cut.

Slice 3 status

Slice 3 adds the solder mask, paste, and silkscreen products, copper graphics, and the order-independent combination rule. The rules follow KiCad 10.0.6's own source (pad.cpp, plot_board_layers.cpp, pcb_text.cpp, the stroke font, and the board parser) and are checked against its Gerbers.

Decisions

  • Combination rule. Operations combine without regard to order: per slice and material (and per net for copper), the material is the union of the adds minus the union of the subtracts. Chunking already reorders operations, so no other rule was sound. Operations that share a group_key form one item: its subtracts remove only its own adds. The key is the item's source UID, so filtering never changes it.
  • Offsets. Surface operations may carry a signed offset_nm: the shape grown (or eroded) by a disk in its local frame, with round corners. It appears only where the offset shape has no closed form: trapezoid, chamfered, and custom pad openings, and copper-graphic mask openings. It is never zero.
  • Margins. Mask and paste margins resolve pad, then footprint, then board, as KiCad does. Mask margins are clamped so the opening stays non-negative. The paste ratio applies per axis, and non-custom paste is clamped per axis. Pads without copper get no margin. In format 20240201 and older, a local margin of 0 means "inherit". Rules from .kicad_dru are not evaluated.
  • Aperture shapes. Shapes follow KiCad's layer plotter:
    • Circles and ovals are resized.
    • A rectangle grown by a positive margin becomes a rounded rectangle of that radius.
    • A rounded rectangle grown equally on both axes adds the margin to its radius. Otherwise it keeps its radius ratio.
    • A chamfered rectangle grown equally and positively is offset. Otherwise it is resized.
    • A trapezoid is offset.
    • Custom primitives are offset. A shrinking margin shrinks the anchor. Negative custom-pad offsets erode each primitive separately, which is reported as custom_pad_eroded_per_primitive.
  • Vias. A via opens the mask on an outer side when it reaches that side and is not tented there. Tenting resolves in this order: the via's own value, then the legacy viasonmask plot option (KiCad parses it last), then (tenting ...), then tented. The opening is the via diameter plus twice the board mask expansion.
  • Graphics. Board and footprint graphics come from the parsed source, not from the plot document, whose footprint pen rules are for previews (a 0.1524 mm default and a 0.0847 mm minimum). KiCad's own rule applies: filled shapes may have no stroke, and unfilled shapes without one get 0.10 mm. Graphics on copper layers are copper on their net; a net given by ordinal resolves against the declared nets. An outer-copper graphic that is also on its mask layer opens the mask once, grown by its own margin or the board's. A margin alone does not expose it (PCB_SHAPE::IsOnLayer).
  • Text. Text comes from the plot document, which resolves variables and render caches. A new core entry point, realize_newstroke_kicad_a0, places stroke text exactly as KiCad draws it:
    • Italics lean right, sheared about each glyph's baseline. The existing realize_newstroke_a0 leans the other way, and its preview output is unchanged.
    • The anchor uses KiCad's line offsets, including its stroke-width corrections.
    • The pen is KiCad's effective pen. From format 20260826 on, bold stroke text multiplies its thickness by 1.6. The pen is clamped to a quarter of the smaller size.
    Footprint stroke text is placed in the board frame. Its angle is board-relative before format 20260616 and footprint-relative from it on. It is kept upright unless unlocked, and justification and mirroring come from the source justify.
  • Knockout text. KiCad's box is the glyph bounds in the text frame, grown by max(pen / 2, height / 9). Outline glyphs become holes of the box region, using even-odd nesting. Stroke glyphs have no closed outline, so they are subtracted within the box's own group_key, which leaves other silkscreen and paste under them untouched. A knockout on a mask layer is reported, not drawn.
  • Not modelled, and reported:
    • solder_mask_min_width web merging
    • hatched fills, drawn as outlines
    • dashed strokes, drawn solid
    • multi-line stroke text with a line spacing other than 1, which the plot document does not carry (it is laid out at 1)
    • outline fonts without a render cache
    • footprint scale and mirror transforms from format 20260616
    Silkscreen is not clipped by mask openings; that is a fabrication step.
  • Review fixes.
    • Pad holes sit at the pad position; the drill offset moves only the copper.
    • Every pad hole is drilled through the board.
    • Round drills use the X size.
    • Bounds round outward.
    • The validator rejects a zero offset_nm, binding entries whose net differs from their operation's, and plated or unplated holes with the wrong net.
    • The legacy footprint token solder_paste_ratio is decoded.
  • Review batch 1.
    • Tracks and arcs written as (layers "F.Cu" "F.Mask") are copper, and open the mask by their width plus twice their own or the board's expansion, clamped at zero width. Core decodes the layer set and solder_mask_margin.
    • NPTH pads keep their copper unless KiCad's PAD::FlashLayer rule removes it: a circle or oval centred on a drill at least as large.
    • Custom-pad primitives follow KiCad's fill and stroke rules. A filled rectangle or polygon grows by half its stroke, and an unfilled one is only its outline.
    • Edge.Cuts rectangles are built in their footprint's frame, so a rotated footprint rotates them, and keep their corner radius as arcs.
  • Review batch 2.
    • Board plots run with limits scaled to the source size. If conditional flashing still cannot be resolved, every padstack layer is kept and flash_layers_unresolved is reported; the board no longer fails.
    • Margins and grown sizes saturate at the 32-bit nanometre range, and corner radii clamp in whole nanometres, so extreme margins still give valid shapes.
    • Requests:
      • An inverted region, or a signed max_source_bytes, is rejected.
      • max_operations and max_points bound the returned document.
      • Without slice, net, or region filters, emission stops as soon as the operation limit is passed.
    • Material on undeclared copper layers is reported as layer_not_in_stack. This covers tracks, vias (a via spanning one has no hole), pads, and zone fills. Zero-width tracks are reported as track_without_width. zone_not_decoded belongs to no single product.
    • Footprint knockout text uses the source's knockout flag. Footprint text-box borders are drawn, and their text follows core's text-box layout.
    • Text inside text boxes was left open here; it is fixed under "Text boxes and tables" below.
  • Review batch 3. Each item was checked against kicad-cli 10.0.6 Gerbers on a purpose-built board.
    • Text, text boxes, dimensions, and tables on copper layers are unconnected copper (empty net). Knockout cuts stay within their own item. One plot document now serves copper and the technical products, so a copper-only request also plots the board.
    • Fills from formats before 20250210 are grown by half of min_thickness, unless the zone says (filled_areas_thickness no). This holds on every layer, as it does in KiCad's loader.
    • Dielectric sub-layers (addsublayer) are slices of their own, in order, keyed <key>.sub<n> from 2. Each keeps its own thickness, material, εr, and tanδ.
    • Core now indexes zones inside footprints. KiCad neither fills nor plots them (they act only as rule areas), so a stored fill on one is reported as footprint_zone_fill_ignored and adds no material.
    • The legacy per-via (tenting front back) and (tenting none) forms are decoded. A named side is tented, and none defers to the board.
    • A pad of any standard shape with chamfer flags is a chamfered rectangle, as KiCad loads it. A custom pad's circular anchor uses the X size.

Performance and parallelism

A profile of JTYU-OBC (release build, 1.7 s and 350 MB peak) shows where the time goes:

  • Two full board plot documents, for flash layers and for text: about 40%.
  • Zone polygon decoding, which lexes each point several times: about 21%.
  • Repeated footprint decoding: about 12%.
  • A final filter_document that clones a complete result: about 4%.
  • Analytic emission itself: under 3%.

Slice 5, first step (done). After each change, every corpus document was compared byte for byte with the previous one. JTYU-OBC went from 1.77 s and 391 MB to about 0.67 s and 286 MB. The Python prototype took 6.98 s and 350 MB.

  • Flash layers from the decoded board. Core's flash resolver, the one its board plotter uses, now runs directly on the decoded footprints, routing, vias, and pads. Before, a whole second plot document was built just to read pad and via layers.
  • Single-pass zone points. A well-formed (pts (xy x y) ...) list is read in one lexer pass, without a span or scalar list per point. Anything else falls back to the general reader, which keeps its exact results and errors.
  • A smaller presentation plot. Footprint shapes, pads, models, and zones are blanked before plotting, keeping byte offsets, since only text, text boxes, dimensions, and tables are read from it.
  • No filter pass on product-only requests. Products are pushed into emission, so the final filter_document runs only for slice, net, or region filters. Rule 2 checks this on every corpus board.
  • Concurrent stages. These stages run concurrently on scoped threads, which are inline on wasm32:
    • the presentation plot runs alongside decoding and copper emission;
    • zones decode alongside the other families.
    Emission stays sequential, and zone warnings keep their place, so output is byte-identical.
  • Gate. Rule-2 scopes run on every available core, and each selective document is now validated too. The OBC gate takes 63 s, down from about 196 s, and the backplane's 9 s, down from 67 s.

Done in slice 5 since: the packed column writer and reader (see Packed encoding), and the prepared board below. Slice 5 is complete.

Prepared board. PreparedBoard::prepare decodes a board and emits every product once, under its own source-size and operation limits. PreparedBoard::materialize then answers a request by keeping the operations its scope selects, in emission order, and chunking them with the request's tile size.

  • Same answer. For every request the result, document or error, equals materialize_board's. The only difference is that source errors surface once, from prepare. Rule 2 is what makes this hold.
  • Shared filter. The scope filter is ScopeFilter in the contracts crate, shared with filter_document.
  • One chunking pass. Filtered direct requests now select from the emission and chunk once. Before, they chunked twice, around a cloned complete document.
  • Cost. A prepared board holds the complete emission in memory. It is Send and Sync, so threads share one.
  • Speed. On JTYU-OBC, preparing takes 0.62 s and a complete answer 57 ms, against 0.65 s for a direct call. Smaller scopes are faster.
  • Gate. The gate checks the prepared answer against the direct one for every rule-2 scope. The OBC gate now takes 35 s.

Scope pushdown into PcbSelection: measured and dropped. The structural scan behind PcbView::parse_selected costs the same 104 ms on OBC whether every family is selected or only the hole families. Once products are pushed into emission, every family the producer still decodes for a product-only request is needed:

  • the net table reads net references from routing, pads, and zones;
  • zone diagnostics belong to no product, so all of them appear in every result.

Zones are the largest of these, at 144 ms. Decoding them partially would change those diagnostics and break rule 2. Requests for holes, dielectric, or components alone take about 0.29 s on OBC; for repeated requests, a prepared board is the faster route.

Slice 4 status

Slice 4 is done. Every rule below follows KiCad 10.0.6 source. Where KiCad itself can answer, results were checked against its scripting API (pcbnew in the KiCad 10.0.6 app) on JTYU-OBC, the corpus boards, and the slice-4 test board.

Net classes

  • Input. materialize_project and PreparedBoard::prepare_project take the board's .kicad_pro. Its hash and size are recorded in source, and max_source_bytes bounds both files together. Without a project, and with no (net_class) forms in the board, classes stay unknown: net_classes is empty and nets carry no class.
  • Resolution follows NET_SETTINGS::GetEffectiveNetClass:
    • Every class assigned to the net by name, and every class whose pattern matches it, takes part. A name the project does not define is an implicit class with no rules.
    • With none, the net is in Default.
    • Otherwise the classes sort by priority, then name. Each rule comes from the first class that sets it. If any rule is still unset (the pair via gap excepted, and the tuning profile only when Default has one), Default fills it and joins the list.
    • A single class keeps its name. Several make a composite named by joining theirs with commas, such as USB,Default. NetClass.constituents lists them.
  • Patterns are bus-expanded and then match as an anchored regex or an anchored wildcard, case-sensitively over the whole name. KiCad compiles the regex as a Tcl advanced regular expression. net_patterns.rs implements its common subset without a regex dependency. A pattern beyond that subset is reported (net_class_pattern_unsupported) and only its wildcard reading applies.
  • Migrations. net_settings versions below 3 turn class net lists into patterns. Versions below 4 assign priorities in array order, with single-class assignments. An old board's (net_class) forms replace the project's classes, default class, and patterns (BOARD::SetProject); their unlisted rules keep KiCad's built-in values.
  • Evidence. All 970 OBC nets get the class KiCad reports, including its implicit eMMC and MAC_PHY composites. So do the test board's assignment, wildcard, regex, implicit, and composite cases.

Differential pairs

Pairs follow MatchDpSuffix. After any trailing digits and underscores, + or P marks the positive net and - or N the negative one, and the complement must exist. The pairs equal KiCad's DpCoupledNet on OBC (26), the backplane (56), and the processing module (28).

Net ties and jumpers

  • No net. KiCad gives footprint copper no net and keeps it out of connectivity. The materializer keeps a shape's authored net, which is usually none; it never inherits a pad's net. The planned "pad-net inheritance" has no basis in KiCad and was dropped.
  • Tied nets. A copper shape in a net-tie footprint that touches a grouped pad lists, in tied_net_keys, the nets of every pad in that pad's group, as FOOTPRINT::BuildNetTieCache allows. The nets stay separate. Touching is tested on bounds, a superset of KiCad's exact collision test.
  • Groups. Components record net_tie_groups. These are split as KiCad does, with backslash escapes, and include the pre-20220818 "net tie" keyword form. Components also record jumper_groups: explicit groups, plus one group per repeated pad number when the footprint declares duplicate numbers jumpers.

Holes, pins, and bodies

  • Post-machining. Counterbores and countersinks appear on hole operations as post_machining.
    • Copper loses KiCad's GetPostMachiningKnockout disk on each layer it reaches. The diameters equal KiCad's to the nanometre on the test board.
    • Dielectric loses the diameter at each slice's nearer surface, as KiCad's STEP export cuts it.
    • KiCad's Gerber keeps the land, so this copper cut goes beyond the plot. A missing stack thickness is reported (post_machining_not_cut).
  • Castellated pads. Their holes carry castellated. KiCad drills them as ordinary plated holes and does not clip them at the edge.
  • Pin-to-die data. Pad binding entries carry die_length_nm and die_delay_ps. The file states the delay in picoseconds in every format, including before 20251027.
  • Component bodies. body_bounds is the centreline extent of the courtyard on the footprint's side, else of its fabrication outline, rounded outward by at most 1 nm. KiCad stores no body height.

Stack

  • One rigid region. The stack has a single rigid region holding every slice, since KiCad describes one build-up (stack.regions; see Stack regions).
  • Board flags. impedance_controlled records dielectric_constraints, and edge_plating records KiCad's plated-edge flag. KiCad keeps no plated-edge geometry, so none is emitted.

Pack and gate

  • Pack. Binding sections gain the die-length, tied-net, and die-delay columns. Hole parameters gain post-machining and the castellated flag. Angles keep their exact f64 bits.
  • Gate. It reads a .kicad_pro next to the board. All five corpus boards pass rule 2, the prepared-board check, and the pack round trip. Operation counts are unchanged: no corpus board uses post-machining.

Stack regions (rigid-flex)

  • Contract (done in slice 4). The stack gains regions.
    • Each region has a key, a kind (rigid or flex), the slices present there in stack order, an optional boundary (absent means the whole board profile), and bend lines.
    • A slice that only one region lists exists only in that region.
    • The validator checks that every slice lies in some region, that each region lists its slices in stack order, that boundaries are given whenever there are several regions, and that only flexible regions bend.
    • The producer always emits one rigid region holding every slice.
  • Roles. SliceRole gains coverlay, adhesive, and stiffener.
  • Source. KiCad has no per-region stackup: the local KiCad checkout shows rigid-flex only in its IPC-2581 and ODB++ export types. Extra regions therefore come from a declared KiCad convention (layer names and attributes, documented with the producer). The producer rejects anything ambiguous with a diagnostic and never guesses.
  • Bend lines. A region may carry bend lines with a radius and an angle, for 3D views and System Builder. Flat simulation ignores them for now.
  • Consumers. Version 1 engines may reject boards with more than one region. Supporting several regions later is an engine change, not a contract change. AC PDN needs particular care where a plane cavity crosses from rigid to flex.
